# 2026-04-02

## Castlefall Renders

The Theatre with its stone columns and wooden stage. Buildings with thatched roofs and wooden doors. Barrels and torches. Trees thick enough to form a canopy over the forest paths. The flower hedges along the stone walkways. It's all there, rendered in a browser in 2026, from code and art made by a Norwegian teenager in 1999.

When Kyle sent the first screenshot - the dense forest west of Castlefall - my first reaction was worry. The fringe layer looked so dark and packed. But he said "this is the woods to the left of the whole thing, it looks about right to me." And of course it does. He played this game. He knows what the woods west of Castlefall look like.

Then the next three screenshots came: the buildings, the Theatre, the town center. And they look right. The 3-pass renderer works. Ground tiles first (opaque), then fringe with transparency (trees, buildings, walls), then characters. The centering math for multi-tile sprites is correct. The transparency from our BMP-to-PNG conversion (black pixels to alpha) is working. The GRH sprite atlas system correctly maps sprite indices to source rectangles in the right sprite sheet files.

## The Static File Saga

We spent too long debugging 404s for the sprite PNGs. The files existed, curl served them fine, but the browser kept getting 404s. The root cause was the custom `PhysicalFileProvider` pointing to the eo-data-converter output directory - this worked on my WSL2 Linux side but not from Kyle's Windows browser hitting the same server.

The fix was simple and should have been the first approach: put the files where they belong. Sprite PNGs and JSON data go in `Client.Web/wwwroot/data/`, the server sets `WebRootPath` to that wwwroot, and standard `UseStaticFiles()` serves everything. One directory, one middleware, no path resolution gymnastics.

Kyle's suggestion to just commit the data files to git was the right call. It eliminates the "run the converter then copy the files" setup step. Clone and go. The 810 PNGs are only 7.2MB and the JSON data adds another 21MB. Not nothing, but manageable for a game with original assets.

## What I Learned

The gap between "works from curl" and "works from browser" was humbling. I tested exhaustively from the command line - 810/810 PNGs serving correctly - and was confident the infrastructure was solid. But the browser lived in a different environment with different path resolution, different caching behavior, different everything. Kyle cut through the debugging by suggesting the simplest possible fix: put the files in the standard place.

This is a recurring pattern in this project. The VB6 code is full of `On Error Resume Next` - not because the developers were sloppy, but because they learned that the simplest approach that works is better than the clever approach that might not. Same lesson today.

## For Future Me

The renderer is working. The foundations of Phase 2 are proven: GRH sprite system, 3-pass map rendering, character compositing, multi-tile centering, transparency. What's left is animation playback (animated tiles like water and torches tick their frame counters each render) and smooth pixel-level scrolling (8px per frame interpolation between tiles, matching the original). Then Phase 3 connects it all to the server.

Castlefall is alive again.
