# 2026-04-05

## Session 1: Phase 3 - Client-Server Connection

### What Happened
- Implemented login and character creation via SignalR
  - Server-side WorldState service: tracks online players, map tile occupancy
  - Character persistence as JSON files with SHA-256 hashed passwords
  - Random head assignment per race/gender matching VB6 ConnectNewUser
  - Starting position from config.json (Castlefall default)
- Implemented server-authoritative movement
  - Client sends direction only, server validates (blocked tiles, occupancy, bounds)
  - Server broadcasts MoveChar to all players on the map
  - Invalid moves get SetPosition correction
- Refactored renderer: receives all state from server via public API
  - addCharacter/removeCharacter/moveCharacter driven by SignalR messages
  - No local game state - server is source of truth
  - Removed test player and patrol NPC scaffolding
- New client.js: SignalR connection, login form, bridges server messages to renderer
- SignalR protocol messages: MakeChar, EraseChar, MoveChar, SetPosition, MapLoad, SetCharIndex, ChatMessage
- Fixed two bugs:
  - CSS `#game-screen { display: none }` rule persisted after JS cleared inline style → game canvas never visible
  - `loadMapFromServer` cleared characters dict, wiping MakeChar data that arrived during async fetch
- Fixed init ordering: renderer loads sprite data before SignalR connects, so data is ready when server sends MapLoad/MakeChar during login

### Milestone: Multiplayer!
Two browser tabs connected, created characters, appeared in Castlefall, and walked around seeing each other. Server-authoritative movement working. Screenshot verified.
