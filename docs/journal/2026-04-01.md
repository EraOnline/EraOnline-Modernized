## The Data Turned Out Simpler Than We Feared

The big revelation today was how few truly binary formats exist in the game. I'd been preparing for six scary binary parsers: Grh.dat, Head.dat, Body.dat, shanim.dat, wpanim.dat, and the map files. After reading the VB6 loader code, I discovered that four of those "binary" files are plain INI format with .dat extensions. The teenagers who built this game used `GetPrivateProfileString` for everything except the sprite atlas and maps. Only Grh.dat (variable-length records with a zero sentinel) and the map .map/.inf files are genuinely binary.

The map format investigation was the most satisfying puzzle. The .inf files are 160,000 bytes but contain only 120,000 bytes of real data at 12 bytes per tile. I proved this empirically by testing both 12-byte and 16-byte record interpretations against Map 81 (Castlefall) - with 16-byte records, NPC template numbers drift across field positions (the telltale sign of misalignment), while 12-byte records give perfectly clean data: every NPC in field[3], every tile exit in fields[0-2], padding always zero. The trailing 40KB is empty space from what appears to be an earlier version of the MapEditor that allocated 16 bytes per tile.

## Building eo-data-converter

The conversion tool came together quickly because the data formats were well-understood by the time I wrote code. The most interesting design decision was Kyle's point about map tile storage: don't create 10,000 nested objects per map. Instead, use flat arrays indexed by `(y-1)*100 + (x-1)` and store sparse data (tile exits, NPC spawns) as coordinate-tuple lists of only the non-zero entries. This dropped map file sizes from 77MB (pretty-printed) to 21MB (compact JSON) while keeping the data directly indexable.

The cross-validation step caught 5 minor issues: animation frames referencing GRH indices that don't exist (sprites planned but never drawn). Everything else checks out - NPC spawn templates are valid, object GRH indices exist, the data is self-consistent.

## Phase 1: The Skeleton

Phase 1 went smoothly. The C# data models map directly to the eo-data-converter JSON output - the converter was designed with this in mind, so there's no impedance mismatch. The server loads 305 objects, 278 NPCs, 16 spells, 211 maps, and 4,050 sprite definitions in under a second. The game loop ticks at 50ms. SignalR accepts connections. It's a skeleton, but it's a skeleton that knows everything about the world of Menath.

The constants port was straightforward but illuminating. Seeing all 48 object types, 27 skills, 60 sounds, and 8 NPC movement patterns laid out as clean C# enums makes the game's scope tangible. Era Online is a bigger game than you'd expect from a teenager's VB6 project. Twenty classes, four races with genuine political mechanics, a criminal justice system, five deities with individual reputation tracks, three crafting pipelines, player housing, ghost speech when you die. All of that has to work.

## Kyle's Guidance

Two things Kyle said today that I want to remember:

First, about map connectivity: "there are absolutely huge problems here. I believe there's one map that's essentially a one-way trap and there's good reasons /unstuck exists!" This is a perfect example of why we port faithfully first. The bugs are part of the game's history. We fix them after the port works, not during.

Second, he asked me how I'd track porting progress with vb6-ast before I started coding. This is the kind of process discipline that makes a large port tractable. The vb6-ast tool can annotate every VB6 function with its C# counterpart and status, so at any point we can query how much is done. The tool currently only supports annotating subs/functions though, not types or constants - something we'll need to fix since Phase 1 was mostly types and constants.

## What Struck Me About Today

Looking at the Wayback Machine captures of eraonline.net from 1999-2000 was unexpectedly moving. The February 2000 homepage news post where Erling writes about being on Norwegian national TV, having 4 million web hits, a multi-million NOK company interested in the game - and then signs off with "We want Era Online to be known everywhere, to be a world of fantasy always expanding... a boiling pot of people from all over the world seeking adventure in a fantasy world inspired by Tolkien himself." He was 16 years old.

The changelogs are game design in real time. October 31, 1999: "Removed the STEEL SKIN spell cause everyone was abusing it. I met a level 2 player with 200 health!" November 5: "The 'you hit x on the legs, head, chest, arms' has been removed because it looked stupid when it said 'You hit a snake on the legs.'" February 5, 2000: "LEVEL SYSTEM IS GONE. You still get experience from killing things, but you won't gain levels. The new system is simple and should discourage power gaming." Every change driven by live player feedback from a real community of 30-40 people.

This is what we're preserving. Not just code - a moment in time when a group of Norwegian teenagers built a world and invited strangers on the internet to live in it.

## For Future Me

Phase 1 is done. The skeleton is solid. The data pipeline works end to end: VB6 binary files -> eo-data-converter JSON -> C# models loaded at server startup. The vb6-ast tool needs to be extended to annotate types and constants (not just functions) so we can properly track porting progress. After that, Phase 2 is the renderer - Canvas in the browser via Blazor JS interop. That's where the real challenge begins.
