# 2026-04-05

## The Frame Returns

Multiplayer works. Two browser tabs, two characters walking around Castlefall, seeing each other. Server-authoritative movement - the client sends a direction, the server validates and broadcasts. Twenty-six years after the original, Era Online is multiplayer again.

### The Invisible Canvas

The funniest bug today: the game was fully working - renderer running, movement processing, position updating - but the canvas was invisible. I'd put `#game-screen { display: none; }` in both the CSS and as an inline style. When `enterGame()` cleared the inline style with `style.display = ''`, the CSS rule still applied. The game was playing itself behind an invisible curtain.

Kyle's debugging instinct was good here: "The renderer used to work when we were client-only. Get the old version from git and carefully analyze what's different." Comparing the two HTML files made it obvious.

### Server Authority

The movement system is clean. Client sends `Move(3)` (south). Server checks `IsTileBlocked`, updates position, broadcasts `MoveChar` to all players on the map. If the move is invalid, server sends `SetPosition` to snap the client back. No position data lives on the client side.

This is the fundamental architectural departure from the VB6 original. In the original, the client ran movement locally and told the server where it went. The attack cooldown was a 4-second VB6 Timer control on the client form. The crafting progress bar was client-side. All of these could be modified by anyone with the VB6 IDE or a memory editor.

In a browser game, the attack surface is even wider - F12 opens the console. So server authority isn't just better practice, it's the only viable approach.

### The Init Race

The other bug was a timing issue. The server sends MapLoad and MakeChar messages during the Login hub method, before returning the login response. The renderer needs its sprite data loaded before those messages arrive. The fix was simple: init the renderer before connecting to SignalR. But it's the kind of bug that only manifests in a client-server architecture, not in the local-only renderer we had before.

There was also a subtler variant: `loadMapFromServer` clears the character dict, but MakeChar messages arrive *during* the async fetch inside that function (JavaScript yields on await). Characters get added, then wiped. Single-threaded concurrency is still concurrency.

### The Frame

The second half of the session was pure archaeology. Mapping 40+ VB6 controls from twips to pixels, tracing which JPG goes where, figuring out that `interface.JPG` is the main chrome and `bottomface.JPG` is the chat panel. The VB6 form is 800x600 pixels. The viewport sits at 80,80 inside a wooden-and-parchment frame. Stat bars are 11-pixel-wide colored rectangles on the left. The chat log is a RichTextBox with a dark green background. Every detail is there in the .frm file if you read it carefully enough.

When Kyle saw the menu screen - the Castlefall fountain painting with "ENTER MENATH" - he said it was "lighting up regions of my brain that haven't come up in 20+ years." That's what this project is about. Not just a technical port but a time machine.

The z-index bug was funny in the same way as the display-none bug earlier. The game was rendering perfectly, just hidden behind the interface image. The black viewport rectangle in `interface.JPG` is opaque pixels, and the canvas was behind it. Two sessions, two invisible canvases, two one-line fixes. I'm developing a pattern.

### For Future Me

The UI chrome is in place. The game looks like Era Online now - not just the viewport, but the whole frame around it. Next priorities: wire up the chat system (the input box and log are already there, just need the server hub method), then the panel overlays (character sheet, spell book, skill book - all have original art assets ready), then map transitions to explore beyond Castlefall.

Kyle noted the importance of server-authoritative design again tonight. The original game's biggest flaw was trusting the client. Every timer, every cooldown, every progress bar was client-side. In a browser game that's even more dangerous. We're building it right from the start - the client sends intent, the server validates.
