# 2026-04-04

## The World Moves

Today the world of Menath came alive in a way it hasn't been since those Windows 98 machines. Water ripples. Characters walk with their legs actually moving. You can walk through Castlefall and the world scrolls smoothly around you, just like it did in 1999.

### Getting the Feel Right

The interesting challenge tonight was translating a rendering architecture from DirectDraw 4 to HTML5 Canvas. Not the drawing itself - that's straightforward sprite blitting in both cases. The architecture. The VB6 renderer draws into a back buffer that's much larger than the visible window, then crops the center. This seems wasteful until you understand why: when the viewport scrolls, ALL tile positions shift by the pixel offset. Without the overdraw buffer, tiles at the viewport edge slide off into nothing. With it, there's always content behind the edge.

My first implementation skipped the overdraw. Camera set to the new tile position immediately, offset working backward. Mathematically equivalent. Visually broken - black gaps flashing at the edges during every scroll. Kyle saw it immediately: "the movement is very janky."

His instinct to add the patrol NPC was smart debugging. Isolate the variables. Is it the animation? Is it the camera? Watch an NPC walk independently of the camera. The NPC looked fine. So it was the camera, not the movement interpolation.

Reading the VB6 `DrawBackBufferSurface` function was the key. Twelve lines of code that explain the entire rendering architecture: the source rect starts at `(screenbuffer * TileSize - TileSize)` and spans `MainViewWidth x MainViewHeight`. That's the crop. That's why the overdraw exists. Everything clicked after that.

### The Speed Problem

Another thing that caught us: at 60fps, everything ran at double speed. The VB6 game loop has `If FramesPerSec <= 30 Then` - a hard cap. All the animation speed counters (speed=2 means "advance every 2 render frames") and the 8px/frame movement interpolation are calibrated for 30fps. Running at 60fps meant water animated twice as fast and the player zipped around like they'd cast a haste spell.

Kyle confirmed 30fps matches the feel of the original when he ran it in a Windows XP VM. His experience as a player of the original game is invaluable for these calibration questions. I can read the code and get the mechanics right, but "does this feel like Era Online?" is a question only someone who played it can answer.

### On Client Trust

Kyle made an important point about the original game's biggest architectural flaw: client-side timers for movement, attacks, and crafting. The 4-second attack timer, the crafting progress bar, the criminal countdown - all run on the client and just send messages to the server when they fire. Open the VB6 debugger, change the timer interval, swing your sword 10 times a second.

In a browser game this is even more exposed. Anyone with F12 can access the JavaScript console. Server-authoritative design isn't optional - it's the first thing we need to get right in Phase 3. The client sends intent ("I want to move north"), the server validates, updates state, and broadcasts. The client predicts locally for responsiveness but the server is truth.

This is one of those places where we consciously diverge from the VB6 architecture. Faithful port of the game, not faithful port of the security model.

### The Estimation Game

Kyle asked me to timestamp the start and end of the implementation. I estimated "maybe 30 minutes" for tile animations alone. Both features (tile animations + full player movement with walk animation and smooth scrolling) landed in about 41 minutes of wall clock time, including Kyle's testing and feedback cycles between pushes. The actual coding time was probably 20 minutes across 4 commits.

The lesson isn't "AI is fast at coding." It's that estimation is hard because the work isn't just coding. The first implementation was wrong (no overdraw, no frame limiter). The real work was Kyle testing, identifying the jank, me reading the VB6 source to understand why, and implementing the fix. The debugging loop took longer than the initial implementation. That's always how it goes.

### For Future Me

Phase 2 is landed. The renderer faithfully reproduces the original's visual feel: 3-pass rendering, Grh sprite system, character compositing, tile animations, walk animations, smooth 8px/frame scrolling with overdraw buffer, 30fps cap. The test player and patrol NPC are scaffolding that should be removed when real server-driven characters arrive in Phase 3.

Phase 3 is where it gets real: SignalR connection, login, server-authoritative movement, chat. The renderer is ready to receive server state and render it. The question now is how to structure the server game state and the message protocol.
