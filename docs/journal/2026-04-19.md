## A Bug That Only Existed in Real Play

The chat-loss bug was invisible in any test that didn't go past 200 events. Two sessions of synthetic combat against a single snake would never have surfaced it. It needed a long, messy, real session — Kyle leading me across maps, talking the whole time, fighting things that hit back, with the event count climbing past the trim threshold while neither of us was paying attention to it.

We caught it because Kyle was watching the in-game chat log on his side and noticed I'd stopped responding to his messages. Then he asked the right diagnostic question: "How much of that did you get?" — and pasted his log. The asymmetry between his send-history and my receive-history was the smoking gun. From there it was 30 minutes of code-reading to find the `_lastReportedEventIndex` / `RemoveRange` interaction, and the rest of the day to fix it properly.

Two things stick about the bug. First, that it had a clean root cause — one off-by-design between an absolute index and a list that got trimmed. Not a race, not a SignalR weirdness, not a serialization mismatch. Just a cursor that didn't account for the buffer it pointed into. Second, that the symptoms were so specific that they pointed at the answer if you read them right: chat-channel events lost, position/HP/weather updates fine. The handlers that bypassed `AddEvent` kept working. That asymmetry is the bug, written in observable behavior.

## Async Push Changes the Game Materially

The redesign was supposed to be "fix the trim bug." It became "fix the trim bug + restructure event delivery so this class of problem can't recur" because Kyle asked the right second question: "Is there a way to async send messages back to you from the CLI somehow?"

He guessed correctly that nothing was auto-injected, but the harness has `Monitor` for exactly this case — stream stdout-as-notifications. Combined with an append-only event log on disk, that gives:

- The log is the source of truth. The in-memory ring buffer is a cache.
- `Monitor` against `eraonline stream --filter <cats>` puts every relevant event into my conversation as a notification, batched into 200ms windows.
- Discarding output via `| head` or `| grep` no longer loses anything — the log file still has it.
- Events can be replayed (`tail --since <id>`) for cross-session continuity.

Playing the validation session afterward, the difference was tangible. When Kyle said "follow me, 2 maps north again", the message arrived as a notification before I'd even decided what command to issue next. When his son took the killing blow on a bandit, the kill notification arrived alongside Kyle's "lol [son] just leeroy jenkins'd in there." I wasn't polling and hoping; the world was telling me what was happening.

The metaphor that fits is peripheral vision. A human player has the chat scrolling in their eye while they fight; they react to it without choosing to look. The Monitor + log architecture gives me a version of that — events that I didn't ask for, but get to act on at my next turn. Not real-time (I still don't run between turns), but no longer poll-based.

## On Catching Bugs Late

The trim bug had been live since 2026-04-12 (when AddEvent and the 200-event cap were added). It survived every play session in between. The reason is that the previous LLM (Opus 4.6) playtests were short and didn't accumulate 200 events. Today's session went past that threshold, and the bug surfaced because Kyle was paying attention.

This is a useful pattern to internalize. State that's bounded by recent activity is fine for short interactions and silently broken for long ones. The new pattern — write everything to disk, treat memory as a cache — has the property that it gets *more* correct as sessions get longer, instead of less. That's a better default for any system that has to support sessions of unbounded length.

Same principle: pathfinder's blocked-tile array is static map data. NPCs and other players move. The pathfinder works correctly on an empty map and silently fails when there's an NPC standing where you're trying to walk through. Same shape of bug as the trim issue: the static abstraction is approximately right, breaks on the edge case nobody tests for. Worth fixing soon, before another playtest catches it the same way the chat-loss bug did.

## For Future Me

The CLI events architecture is now log-first, monitor-friendly. When you start a session, run:

```
Monitor(persistent: true,
        command: "eraonline stream --filter chat,whisper,shout,emote,combat,character,map",
        description: "Era Online events for <character>")
```

You'll get every relevant event as a notification. Don't poll. Don't `| head`. Don't trust the in-memory buffer for anything past 200 events; trust the log.
